Part 02 · Proposed collection

Four linked data products

The final collection is organized as four deliverables. Stable run and timestamp identifiers connect every raw record to processed outputs, route context, and event windows.

01Raw dataOriginal observations
→
02Structured dataSynchronized and processed
→
04Event dataIndexed disengagement windows
03Infrastructure dataRoad and environment context joined to runs and events by position and time
01
PRIMARY RECORD

Raw data

Purpose
Preserve original sensor, vehicle, and system measurements for replay and reprocessing.
Example contents
Camera, LiDAR, radar, GNSS/IMU, CAN, actuation feedback, and raw autonomy topics.
Planned format
MCAP / ROS bag, video or image files, point clouds, and timestamped CSV.
Connection
Source for processed outputs; event records point back to exact raw time windows.
02
ANALYSIS-READY RECORD

Structured / processed data

Purpose
Provide synchronized, quality-checked records that can be compared across runs.
Example contents
Objects, lanes, drivable space, localization, trajectories, commands, vehicle states, confidence, and annotations.
Planned format
Parquet or CSV tables with JSON metadata and GeoJSON where spatial records are required.
Connection
Derived from raw data and joined to infrastructure and event tables through run, time, and location keys.
03
CONTEXT RECORD

Infrastructure data

Purpose
Describe the road and operating environment in which each AV record was produced.
Example contents
Road geometry, lane markings, surface condition, signs, intersections, shoulders, work zones, and visibility.
Planned format
GeoJSON or Lanelet2 layers, route tables, geotagged images, and inspection records.
Connection
Provides spatial context for complete runs and for the road segment surrounding each event.
04
RESEARCH-FOCUSED RECORD

Event data

Purpose
Make disengagements and other safety-relevant transitions searchable and directly reviewable.
Example contents
Degradation, warning, disengagement, takeover, manual-control, recovery, causes, outcomes, and derived variables.
Planned format
Event table, metadata JSON, synchronized video clips, and linked pre-event / post-event data windows.
Connection
Acts as an index into the corresponding raw, structured, and infrastructure records.

Part 03 · Central research topic

Disengagement Events

A consistent event definition makes it possible to connect system behavior, driver action, road context, and vehicle recovery without treating every term as interchangeable.

WORKING DEFINITION

A disengagement event is a transition in which automated driving is terminated, either by the system or through human intervention.

01SYSTEM ATTRIBUTEDegradation

Performance or confidence begins to decline.

→
02SYSTEM ACTIONWarning / request

The system issues an alert or takeover request.

→
03CENTRAL EVENTDisengagement

Automated driving mode ends.

→
04RESPONSETakeover / fallback

The driver intervenes or the system executes fallback.

→
05STATEManual control

The driver controls the vehicle after automation ends.

→
06OUTCOMERecovery

The vehicle returns to a stable operating state.

Not every event must contain every stage. The event record preserves which transitions occurred, their order, and their timestamps.

Consistent terminology

One event, distinct stages and attributes

“Disengagement event” is the central record. The remaining terms describe a precursor, trigger, response, state, outcome, or possible cause.

System degradation
A measurable reduction in perception, localization, planning, or control performance.
Warning / takeover request
A system notification asking the driver to prepare or assume control.
Takeover / intervention
The driver’s action to assume control; it may initiate or follow disengagement.
Manual control
The vehicle operating state after the driver has assumed control.
Recovery
The stabilization of the vehicle and completion of the immediate response.
Failure
A cause or attribute of an event—not a synonym for every degradation, intervention, or disengagement.

Event-data deliverable

What one disengagement record contains

  1. 01

    Event identityRun ID, event ID, location, start time, disengagement time, and end time.

  2. 02

    System sequenceDegradation indicators, warnings, mode transitions, faults, and automation status.

  3. 03

    Human responseIntervention type, reaction time, manual-control onset, and driver inputs.

  4. 04

    Linked evidenceReferences to raw sensors, processed outputs, route infrastructure, and synchronized event windows.

  5. 05

    OutcomeMinimum safety margin, recovery behavior, final vehicle state, and review labels.

Part 04 · AV Stack and data

How the AV system produces the dataset

DataSpeed and Autoware are the development bases. Their sensor, autonomy, vehicle-interface, and system-state outputs are recorded and transformed into the four connected data products.

01 · VEHICLE PLATFORM

DataSpeed

Provides drive-by-wire integration, CAN and vehicle-state feedback, actuation commands, and the interface between autonomy software and the vehicle.

02 · AUTONOMY PLATFORM

Autoware

Provides sensing, perception, localization, planning, control, system operation, diagnostics, and automation-state outputs.

01RECORDVehicle + AV stack

Capture sensors, autonomy topics, CAN, commands, feedback, modes, and diagnostics.

→
02ALIGNTime synchronization

Assign common clocks, coordinate frames, route IDs, run IDs, and data-quality flags.

→
03ENRICHProcessing + context

Generate objects, lanes, trajectories, states, annotations, and route-infrastructure joins.

→
04DELIVERRuns + events

Publish linked raw, structured, infrastructure, and disengagement-event records.
